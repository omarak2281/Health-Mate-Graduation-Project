# API Documentation

Base path: `/api/v1`. Interactive Swagger docs are auto-generated by FastAPI at `/docs` when the backend is running. This document is built directly from the router source files and their Pydantic schemas (`app/schemas/`, `app/api/schemas/`, `app/application/dto/`) — every request/response shape below reflects an actual model class, not an assumed convention.

Two authentication schemes exist side by side (`BACKEND.md` §1):

- **Bearer JWT** — `Authorization: Bearer <access_token>`, for all human-user endpoints.
- **Device headers** — `X-Device-ID` + `X-Device-Token`, for the two BP hardware endpoints only (`/vitals/bp/submit`, `/vitals/bp/heartbeat`).

## 1. Authentication (`/auth`)

### `POST /auth/register`

- **Purpose**: Create a patient or caregiver account.
- **Auth**: None.
- **Request** (`UserRegister`): `email`, `password` (8–100 chars, must contain a digit and an uppercase letter), `full_name`, `phone?`, `role`(`patient`|`caregiver`), `firebase_uid?`, `profile_image_url?`, `linked_patient_id?` (caregiver auto-links to this patient on signup if provided).
- **Response**: `201` + `UserResponse` (id, email, full_name, phone, birth_date, gender, role, profile_image_url, is_active, is_verified, firebase_uid, auth_provider, created_at).
- **Validation**: Pydantic rejects a weak password before the handler runs; the handler itself rejects a duplicate email (`400`).
- **Notable behavior**: if the caller supplied a `firebase_uid` and the database insert fails for any reason, the handler explicitly deletes the orphaned Firebase user (`delete_firebase_user`) rather than leaving an account that exists in Firebase but can never log in — a real rollback safeguard, not just a caught exception. A successful registration also writes an `AuditLog` row (`event_type="user_registered"`).
- **Errors**: `400` duplicate email; `422` validation failure; `500`unexpected DB failure (with the Firebase-cleanup behavior above).

### `POST /auth/login`

- **Purpose**: Email/password login.
- **Auth**: None.
- **Request** (`UserLogin`): `email`, `password`, `firebase_id_token?`, `role?`.
- **Response**: `200` + `Token` (`access_token`, `refresh_token`, `token_type="bearer"`).
- **Errors**: `401` on bad credentials or inactive account.

### `POST /auth/refresh`

- **Purpose**: Exchange a refresh token for a new access/refresh pair.
- **Auth**: Refresh token as a request parameter (not a header).
- **Response**: `200` + `Token`.
- **Validation**: rejects if the token doesn't decode, isn't tagged `"type": "refresh"`, or the user no longer exists/is inactive (`401`).
- **Known gap** (`BACKEND.md` §1): the old refresh token is not invalidated when a new one is issued — no server-side token store exists to revoke it.

### `POST /auth/social`

- **Purpose**: Firebase-based login/signup (Google Sign-In etc.).
- **Request** (`SocialAuthRequest`): `firebase_id_token`, `role?` (required for a new account), `is_signup`, `phone?`, `birth_date?`, `gender?`.
- **Response**: `Token`.

### `POST /auth/verify-email`

- **Purpose**: Mark a user's email as verified (Firebase-issued token flow).

### `POST /auth/logout`

- **Purpose**: Stated as ending a session.
- **Real behavior**: returns a success message and does nothing else — no token is invalidated server-side (`BACKEND.md` §1, straight from the handler's own docstring).

## 2. Users (`/users`)

| Endpoint | Method | Purpose |
| --- | --- | --- |
| `/users/me` | GET | Current user's profile |
| `/users/me` | PUT | Update profile (`UserUpdate`: full_name, phone, birth_date, gender, profile_image_url) |
| `/users/me/fcm-token` | PUT | Register/update the device's FCM push token |
| `/users/me/password` | PUT | Change password (`PasswordChange`: current + new, same strength rule as registration) |
| `/users/linked` | GET | Caregivers (if caller is a patient) or patients (if caller is a caregiver) |
| `/users/link/{user_id}` | POST | Link current user with another user by ID — see `BACKEND.md` §1 for the QR-code caveat |
| `/users/linked/{user_id}` | DELETE | Deactivate a patient–caregiver link |
| `/users/me` | DELETE | Delete own account |

All require Bearer auth. `POST /users/link/{user_id}` validates the role combination (one side must be `patient`, the other `caregiver`; two patients or two caregivers linking is rejected with `400`), reactivates a previously deactivated link if one exists, assigns the "primary caregiver" flag via `patient_caregiver_service.assign_is_primary_for_new_link` (respecting the one-active-primary-per-patient DB constraint, `DATABASE.md` §3), and auto-adds the caregiver to the patient's medical contacts as a `FAMILY`contact (de-duplicated by normalized phone number).

## 3. Vitals / Blood pressure (`/vitals`)

The most behaviorally rich router in the backend — full detail (calibration state machine, risk classification, alerting) is in `BP_PREDICTION.md` §14 and `BACKEND.md`; this section is the endpoint reference.

| Endpoint | Method | Auth | Purpose |
| --- | --- | --- | --- |
| `/vitals/bp` | POST | JWT | Manual BP entry (`VitalSignCreate`) |
| `/vitals/bp/submit` | POST | Device headers | Hardware submits an 800-sample PPG+ECG window; runs model inference + calibration |
| `/vitals/bp/complete` | POST | JWT | Patient supplies a cuff reading to finalize a `completed_pending_bp` reading, also recording a calibration sample |
| `/vitals/bp/heartbeat` | POST | Device headers | Device reports finger/lead status |
| `/vitals/bp/history` | GET | JWT | Paginated reading history |
| `/vitals/bp/stats` | GET | JWT | Aggregate statistics for charts |
| `/vitals/patient/{patient_id}/*` | GET | JWT (caregiver) | Same views, for a linked patient |

### `POST /vitals/bp/submit` request/response detail

- **Request** (`VitalSignDeviceSubmit`): `device_id`, `ppg_signal` (exactly 800 floats — a length mismatch is rejected by the schema itself, `422`, before the handler runs), `ecg_signal` (exactly 800 floats), `heart_rate?`(0–250, sanity-bounded but wide since it's device-computed), `spo2?`(0–150 — deliberately wider than physiologically valid so a bad on-device SpO2 computation never fails the whole submission; the handler nulls anything outside 70–100 rather than rejecting the request).
- **Response**: `201` + `VitalSignResponse` — but with `systolic`/`diastolic`possibly `null` if `measurement_status` came back `completed_pending_bp`(calibration not yet trusted enough to show a number, `BP_PREDICTION.md`§14).
- **Errors**: `503 model_not_ready` if the BP model artifacts aren't loaded; `422` for a malformed/wrong-length signal payload; `401` for bad device credentials.

### `POST /vitals/bp/complete` request/response detail

- **Request** (`CuffCompleteRequest`): `vital_sign_id`, `systolic` (50–300), `diastolic` (30–200); schema-level validator rejects `systolic <= diastolic` before the handler runs.
- **Response**: `200` + the finalized `VitalSignResponse`.

## 4. Medications (`/medications`)

Standard CRUD plus adherence logging and smart-box assignment:

- **Create** (`MedicineCreate`): `name`, `dosage`, `times_per_day` (1–3), `scheduled_times` (list of `HH:MM` strings — schema validates the format and that the list length exactly matches `times_per_day`), `use_smart_box`, `drawer_number?` (1–6, **required** if `use_smart_box` is true — enforced by a model-level validator, `422` otherwise).
- **Adherence** (`MedicationAdherenceCreate`): optional `image_url` (proof photo) and `taken_at`.
- Full schedule/alarm/smart-box trigger behavior is in `BACKEND.md` §3 and `IOT.md` §2.

## 5. BP reminders (`/bp_reminders`)

- `POST /bp_reminders/schedule-daily` — derives up to 3 daily reminder times from one patient-chosen start time (start, +8h, +16h, wrapping midnight — `bp_reminder.py`'s own module docstring).
- `GET /bp_reminders` — list configured reminders.

## 6. Notifications (`/notifications`)

- `GET /notifications` — list, paginated.
- `GET /notifications/unread-count`.
- `PUT /notifications/mark-read` (`NotificationMarkRead`: list of notification IDs).
- `PUT /notifications/{id}/read` — mark one as read.
- `DELETE /notifications/{id}`.

`NotificationResponse` includes `notification_type` (one of the ten values in `NotificationType`, `DATABASE.md` §1), `title`, `message`, a free-form `data` JSON blob (e.g. `{"bp_reading": "180/120", "risk": "critical"}`), and `is_read`.

## 7. Medical contacts (`/contacts`)

Standard CRUD (`MedicalContactCreate`/`Update`/`Response`): `name`, `phone`, `contact_type` (`doctor`|`clinic`|`pharmacy`|`emergency`|`family`), `notes?`.

## 8. Calls (`/calls`)

WebRTC session lifecycle, paired with the Socket.IO signaling events in `ARCHITECTURE.md` §2.3:

| Endpoint | Method | Purpose |
| --- | --- | --- |
| `/calls` | POST | Start a call (`CallStartRequest`: `callee_id`, `call_type`) |
| `/calls/{call_id}` | GET | Fetch call state |
| `/calls/{call_id}/offer` | POST | Attach an SDP offer (`CallOfferRequest`) |
| `/calls/{call_id}/accept` | POST | Accept |
| `/calls/{call_id}/reject` | POST | Reject |
| `/calls/{call_id}/busy` | POST | Mark busy |
| `/calls/{call_id}/end` | POST | End, records `duration_seconds` |

`CallSessionResponse` carries `status` through the full lifecycle (`idle → ringing → in_call → ended`, or `rejected`/`busy`/`missed`/`failed`). The REST endpoints establish/persist call state; the actual SDP/ICE exchange happens over the Socket.IO channel, not these HTTP calls.

## 9. IoT (`/iot`) and Hardware (`/hardware`)

- `GET /iot/sensors/status`, `GET /iot/sensors/data` — **simulated** data from `iot_mock.py`, regardless of `iot_mode` setting (`BACKEND.md` §4 — a real, verified discrepancy, not a documentation assumption).
- `GET /iot/medicine-box/status`, `GET /iot/medicine-box/drawers` — real ESP32 state via `esp32_service.ping()`.
- `POST /iot/medicine-box/deactivate-all` — turns off all drawer LEDs/buzzer.
- `GET /hardware/status` — ESP32 reachability ping.

## 10. Symptom checker / AI (`/ai`)

Both symptom-checker generations are exposed here; full behavioral detail (including the rule engine, calibration between the two implementations, and honest accuracy figures) is in `SYMPTOM_CHECKER.md`. Endpoint reference:

| Endpoint | Method | Generation | Purpose |
| --- | --- | --- | --- |
| `/ai/available-symptoms` | GET | v1 | Symptom list for the legacy flow |
| `/ai/symptom-checker` | POST | v1 | Category/symptom-list → prediction |
| `/ai/chat` | POST | v1 | Free-text conversational symptom chat |
| `/ai/model-info` | GET | both | Loaded model metadata |
| `/ai/symptom-checker/history/{session_id}` | GET | v1 | Past chat turns |
| `/ai/categories` | GET | v2 | Specialty categories |
| `/ai/taxonomy/symptoms` | GET | v2 | Symptom taxonomy, optionally filtered by category |
| `/ai/assessment` | POST | v2 | Structured assessment (`AssessmentRequestSchema`) → `AssessmentResultDTO` |
| `/ai/bp-triage` | POST | v2 | Same as `/assessment`, plus a `should_remeasure` override for borderline-high vitals-driven cases |
| `/ai/chat/from-assessment` | POST | v2 | Seeds a chat session with assessment context |
| `/ai/assessment/notify-caregiver` | POST | v2 | Explicit caregiver notification trigger, returns `CaregiverNotificationResponse` (`notified_count`, `auto_triggered`) |
| `/ai/assessment/rollout-metrics` | GET | v2 | In-process counters: assessment count, red-flag rate, caregiver-notification rate, latency (`BACKEND.md`-adjacent, `symptom_checker_metrics.py`) |

### `POST /ai/assessment` / `/ai/bp-triage` request shape (`AssessmentRequestSchema`)

`source_vital_id?` (UUID — links the assessment to the `VitalSign` that triggered it, `DATABASE.md` §3), `category_id?`, `symptoms` (list of `{id, severity 0–4}`), `duration_days?`, `age_group?`(`child`|`adult`|`elderly`), `known_conditions` (list of strings, used as risk factors), `vitals?` (`systolic`, `diastolic`, `heart_rate`, `spo2`).

### Response shape (`AssessmentResultDTO`)

`top_predictions` (list of `{disease_id, name, confidence, why, why_names}`), `urgency` (`low`|`moderate`|`high`|`critical`), `urgency_label` (localized), `red_flags` (list of `{code, name, severity}`), `patient_message`, `recommended_action_code` + `recommended_action_text`, `caregiver_summary`, `should_notify_caregiver`, `should_remeasure`, `disclaimer`. All templated text is bilingual (`en`/`ar`) via the `lang` query parameter; the optional LLM phrasing layer (`SYMPTOM_CHECKER.md` §6) may rewrite `patient_message`/ `caregiver_summary` only, never the urgency or predictions themselves.

### Error contract for `/ai/*` v2 endpoints

`ErrorResponse` (`error_code`, `message`) — the code is documented as the stable, parseable field; Flutter is expected to branch on `error_code`, not parse `message` text, keeping error handling language-independent.

## 11. Upload (`/upload`)

`POST /upload/image`, `/upload/public/image`, `/upload/profile-picture`, `/upload/medication-image` — all Cloudinary-backed (`cloudinary_service.py`). Returns `503` if Cloudinary credentials aren't configured in the environment, rather than silently failing. `DELETE /upload/image/{image_id}` removes a previously uploaded asset.

## 12. Realtime (Socket.IO, not REST)

Mounted at `/ws` and `/socket.io` in `main.py`, authenticated with the same JWT via a `connect` handshake. Events: `join_room`, `make_offer`, `make_answer`, `send_ice_candidate`, `call_declined`, `call_ended` — all scoped to a `user:{id}` room. Not reachable via the interactive `/docs` UI since it isn't a FastAPI route; documented here because it's part of the same API surface a client integrates against. Full context in `ARCHITECTURE.md` §2.3.
